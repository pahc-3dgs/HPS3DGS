# HPS3DGS 验证与验收范围

验证的目标是证明本次修改所影响的行为。整合、测试通过、代表包可重建和算法达到目标是不同结论，报告必须分别写出。未知、未运行、跳过或缺少参考值均不能记为通过。

## 1. 三类结论

| 结论 | 必须有的证据 | 不能由此推出 |
|---|---|---|
| 代码检查通过 | 最终提交、来源/依赖检查、适用的 CPU/格式/几何测试及实际结果 | 所有历史模型都可运行，或算法性能已达标 |
| 代表包独立解码与重建通过 | 包哈希、新进程解码、格式匹配、相机/输入协议、实际渲染和预先约定容差内的指标 | 未测试格式/场景都通过，或具有 held-out 泛化能力 |
| 算法目标达成 | 明确目标、可比实验协议、完整目标场景、控制变量和足够证据 | 仅凭文件迁移或一个 smoke test 达成 |

同一组 150 视图用于训练和评价时必须写作 `150 train / 150 reconstruction views（同一组视图）`。这可以验证重建与迁移一致性，不能称作未见视图测试。`codec_only` 后端包可移植只支持编解码结论，不支持稳定模板归属传播或 owner-aware 联合训练的结论。

## 2. 必要记录

每次验收记录下列信息，保存到新的输出目录，并由变更报告链接到它：

- 主仓库完整 HEAD、分支、未提交状态，各级子模块固定提交与实际提交；相关版本来源/恢复材料。
- 输入场景、checkpoint、压缩包的路径、字节数和 SHA256；相机/视图列表及列表哈希；输出目录。
- 实际命令、环境变量中的非敏感必要项、Python/PyTorch/CUDA 和扩展真实加载位置；GPU 编号与运行时间。
- 检查名、预期、实际值、容差、退出码和状态 `PASS / FAIL / NOT_RUN / BLOCKED / NOT_APPLICABLE`。`NOT_APPLICABLE` 需说明与本次修改无关的原因。
- 日志、解码/渲染产物和视觉核对结果；尺寸统计区分 codec streams、共享解码器参数及完整便携包，并明确 MB 或 MiB。

不要把鉴权信息写入报告。引用历史结果时保留来源，不能把旧环境、旧提交或不同评价协议的记录改成当前提交的测试记录。

## 3. 分层检查

统一运行接口为：

```bash
python scripts/validate_release.py --profile source --runtime configs/runtime.4090.json --output <新的来源检查目录>
python scripts/validate_release.py --profile cpu --runtime configs/runtime.4090.json --fixtures configs/validation.4090.json --output <新的CPU检查目录>
python scripts/validate_release.py --profile gpu --runtime configs/runtime.4090.json --fixtures configs/validation.4090.json --output <新的GPU检查目录>
```

这里的 `<...>` 是必须替换的路径，不是直接可执行参数，输出目录必须尚不存在。CPU/GPU fixture 文件由 `--fixtures` 指定；默认位置以验证器帮助为准。实际检查清单以验证器帮助及配置为准；不能通过一个 `gpu` 选项就假定所有路线/格式已经覆盖。缺少某条路线所需的 fixture、参考结果、环境或执行实现时，该项保持 `BLOCKED` 或 `NOT_RUN`，不能返回通过。

结果写入各自的 `report.json`，至少包括 `status`、`profile`、`root_head`、`repositories`、测试结果、实际命令及退出码。验证器以退出 0 表示配置内检查通过，非 0 表示失败或未完成；合入前还需核对该配置是否覆盖本次全部必需项目。当前未部署 CI 的检查按这些本机命令执行，不声称已有自动远端 CI。

合入前运行 `scripts/check_merge.py --release-root <候选工作树> --reports <各报告路径> --require source cpu gpu`，核对报告中的 `root_head`、`code_manifest_sha256`、递归依赖提交及实际检查状态与当前候选一致。门禁不修改 Git、不合并、不推送。纯文档修改可按范围只要求 source，仍需说明其它 profile 不适用；完整发布不能减少必需范围。

| 层级 | 检查内容 | 通过条件 |
|---|---|---|
| `source` | 干净工作树、文件来源、依赖固定、`release_manifest.json` 文件 SHA256、必要脚本和配置、基本语法/入口、路径引用 | 无遗漏源码；清单哈希与实际文件一致；实际依赖与固定提交一致；源码来自新整合目录或明确固定的依赖 |
| `cpu` | 现有可在 CPU 执行的 codec、量化、几何/实例和配置测试 | 本次必需用例通过；至少覆盖所修 bug 的失败条件，不把缺依赖跳过算通过 |
| `gpu` | 对应路线导入/扩展检查，代表包新进程解码/渲染；必要时短训练 | 实际产物存在且有效；数据和协议匹配；行为/指标在预先记录容差内 |
| 算法实验 | 研究任务明确要求的场景、种子和目标指标 | 完成所需对照及目标评价，单独报告结论 |

已验证的 GPU 运行环境可以复用，但要检查扩展真实来源。源码迁移后仍加载旧工作树中的 Python 文件或可编辑安装，来源检查不通过；复用明确配置的共享二进制扩展时必须记录其来源和版本，不把它描述为已经可从新源码重建。

修改清单覆盖文件后，先 `git add` 本次明确文件路径，再运行 `python scripts/release_manifest.py refresh --output release_manifest.json`，随后 `git add -- release_manifest.json` 并提交，最后做正式检查。刷新器要求递归子模块干净并匹配父 gitlink，拒绝未忽略的未跟踪文件；不会自动暂存、提交或联网。主仓库可在刷新时有已跟踪改动，但 source、CPU、GPU 三个正式 profile 开始和结束时均要求主仓库及递归依赖干净、固定版本和清单一致。LFS payload 不计入源码哈希，指针身份单列；这不代表权重已通过运行验证。

CPU profile 复用主仓库 `unittest discover`、SegAny 的 Geo33 几何测试和 Fig. 7 packet 测试，并通过 `--fixtures` 中的 `canonical_point` 运行 canonical 检查。当前运行环境使用 unittest，不要求安装 pytest。报告记录真实执行数量及跳过情况；必需项目的零用例、skip 或缺 fixture 都不能记为已通过。

整合阶段的内部预检可以用于定位遗漏，但只要跳过了干净工作树或哈希校验，就不能列为正式 source 通过。初次整合未完成全部发布验收时保留候选分支/标签，不将其推进为已验收 main。

## 4. 根据改动决定验证范围

| 改动 | 合入前要求 |
|---|---|
| 仅文档/注释 | 检查 diff、路径和命令的一致性；无需 GPU 或新增行为测试 |
| 配置路径/启动入口/环境路由 | 来源检查、入口参数/路径检查；实际调用受影响路线，对有效输入至少执行一次对应 smoke |
| 几何、实例变换、量化或包读写 | 对应现有 CPU 测试和故障回归；受影响格式代表包独立解码，必要时渲染比较 |
| HAC 或 HAC++ 后端适配、依赖指针 | 子模块局部测试，父仓库跨组件测试，该后端代表包独立解码/渲染；不能用另一个后端代替 |
| 训练参数传递、数据加载、保存行为 | 数据/相机检查与短训练 smoke，核对 checkpoint 内容；如影响目标指标，再执行任务要求的可比实验 |
| 码流格式变化 | 显式格式版本；旧包兼容解码或明确可判定的拒绝；新格式往返及渲染，记录兼容范围 |
| 初次整合正式发布 | 所有保留入口/格式的适用检查和代表包验证；新目录恢复及递归依赖恢复；记录仍未证明的算法目标 |

局部修复不默认重训所有场景。已经通过的检查只有在新改动、失败或未解决疑点影响其结论时才扩大或重复。首次整合若只能完成 source/CPU，则报告“代码整合及已列检查完成，GPU/代表包验收未完成”，保持候选状态。

## 5. 各路线分别验收

| 路线/格式 | 必须保持的边界 | 代表验证 |
|---|---|---|
| 原 PAHC | 原压缩/解码入口和自己的参数约定 | 对应 PAHC fixture/包的往返或独立解码 |
| Fig. 7 | Geo32 的优化、五组 PTQ、Fig. 7 解码；阈值点独立运行 | Fig. 7 包、非空实例及变换/量化测试，所需渲染比较 |
| Geo33 原生包 | 四组 QAT 与 Geo33 原生字段/解码 | 原生包独立解码及变换/参数核对 |
| Geo33 紧凑存储包 | 位打包、FP16/坐标精度等各自配置 | 存储格式测试；声明支持的模式/参数需有覆盖记录 |
| HAC 便携包 | 原生 HAC 模型、算术编码与独立适配器 | HAC 包新进程解码、实际渲染及相同协议指标 |
| HAC++ 便携包 | 原生 HAC++ 模型、坐标/熵编码及独立适配器 | HAC++ 包新进程解码、实际渲染及相同协议指标 |

不要拿 Geo33 解码器解释 Fig. 7 的 SH-rest 行为，也不要用 HAC++ 路径替换成 HAC 路径来宣称兼容。模板实例相关验证至少包含一个确实存在实例的输入；仅有空实例 fixture 不足以验证共享/变换逻辑。

## 6. 代表包验证步骤与停止条件

1. 先选择已有参考包和基线，记录包与输入哈希、格式、场景、相机列表、实际参考指标和容差。容差由当前路线数值精度与原比较协议决定，在看到修复后结果前记录；不为得到通过而事后放宽。
2. 在新进程使用整合目录的解码入口和明确环境。解码只能依赖便携包、声明的运行环境及评价所需相机/真值；若仍读取训练目录中的权重，不能称为 bundle-only。
3. 检查解码张量/点数、有限值、关键参数、实例变换及生成产物，再做实际渲染。进程启动成功和文件存在均不足以证明内容有效。
4. 按同一视图、背景、颜色/尺度及尺寸协议比较渲染和指标，查看代表图像。验证报告同时保留参考与新值，不能只写“差异很小”。
5. 如行为异常，保存最小复现及日志，在 `fix/` 分支处理。通过后将最终提交、证据目录和结论填入变更报告。

以下任一情况应阻止受影响范围的合入/正式发布：主仓库或子模块待验收源码脏；固定提交无法恢复；仍有隐式旧源码依赖；必需用例失败或未运行；没有匹配格式的代表包；视图/输入/环境与参考不匹配；指标超出预先约定容差；产物无效；恢复演练失败。

非必要项可以按改动范围标为 `NOT_APPLICABLE`，但原因必须可核对。例如文档修正不要求渲染；初次正式发布不能用该理由跳过某个保留后端。测试基础设施本身未实现时，状态是未完成，不是已通过。
